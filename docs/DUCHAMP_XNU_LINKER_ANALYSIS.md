# SWEET ARM64 XNU link analysis

## Link failure and reference

The first WSL probe ran `/usr/bin/ld64.lld` (Ubuntu LLD 21.1.8) on only the rebuilt `memdev.o` and `IOKitBSDInit.o`. Its [argv and exit status](../../../outputs/duchamp-dual-ramdisk-integration-20261116/xnu-linker-capability.command.json) are retained. Undefined `_main` and XNU helpers were expected for that input set. The `-segment_order` warning exposed a separate linker limitation.

The [new link probes](../../../outputs/duchamp-full-xnu-source-build-20261117/link-probes.json) record complete argv for both linkers, including the Clang `-###` invocations. The probe used the saved `.LDFLAGS` from CI 41340697398 and the unchanged objects archive from CI 41543710742 as a diagnostic input. It relocated the two available side files, then attempted to resolve the original `-lfirehose_kernel` and `-lcc_kext` dependencies. It did not substitute stub libraries or produce a modified kernel.

| Probe | Observed output |
| --- | --- |
| LLVM 21.1.8, self-contained ARM64 entry and three segments | Exit 0. It ignored `-static`, `-image_base` and `-segment_order`. The file used a userspace base, placed `__DATA` before `__TEXT_EXEC`, and emitted `LC_LOAD_DYLINKER` and `LC_MAIN`. |
| LLVM 21.1.8, CI archive and reconstructed CI flags | Exit 1. The Linux Clang driver did not supply the LLD-required platform version for this static recipe. Explicit `-platform_version macos 15.5 15.5` got past that error. LLD still ignored the static, base, ordering and alias options, failed to find `libfirehose_kernel`, and reported unresolved `___chkstk_darwin` and Mach VM aliases. |
| cctools-port, Darwin Tools for Linux v2.4.0, ld64-951.9 | Exit 0 for the same minimal input. It placed the executable at the requested high VA, honored the three-segment order, and emitted `LC_UNIXTHREAD`. Full-arguments archive probes exited 1 on missing `libfirehose_kernel`, with and without the modern linker selector. Full XNU compatibility remains unverified. |
| Archived working CI image | ARM64 ALL, `MH_EXECUTE`, `NOUNDEFS` and `PIE`. `LC_BUILD_VERSION` reports macOS SDK/minimum 15.5 and ld **955.13**. SHA-256 `e465723a540844817a5b9cb36c14984d660f9a8e41f6638240527b469189182b`. Kept as a format and regression reference. |

Three independent gaps remain on the local host. The LLD kernel link semantics differ. The saved tree omits the complete object set and support libraries. The known full build uses a Darwin SDK/tool chain to generate these inputs, including Darwin MIG tooling, the pinned IIG outputs, Xcode's `libcc_kext` and the arm64 slice of `libfirehose_kernel.a` built by dxb. A port of ld64 alone does not supply them. The SWEET link flags have no platform-specific `KernelSupport/libSWEET...` force-load rule. The pinned dxb still requires the 13.5/22G74 KDK path for its build setup.

Primary references are [LLVM Mach-O options](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/lld/MachO/Options.td), [Apple ld64 option parsing](https://github.com/apple-oss-distributions/ld64/blob/main/src/ld/Options.cpp), [the tested Darwin Tools release](https://github.com/kabiroberai/darwin-tools-linux/releases/tag/v2.4.0), and [the pinned dxb script](https://github.com/blacktop/darwin-xnu-build/blob/663906528d1cd5ea8fde7de6f16de73db9511549/build.sh).

## Input recipe and image contract

- XNU `makedefs/MakeInc.kernel` links using `$(LD) $(LDFLAGS_KERNEL) $(LDFLAGS_KERNEL_ONLY) -filelist link.filelist version.o ... -o $@ $(LD_KERNEL_LIBS) $(LD_KERNEL_ARCHIVES)` in the non-LTO configuration. `$(LD)` was the Xcode 16.4 Clang++ driver. `makedefs/MakeInc.def` defines static linking, `-e __start`, the image base, explicit section relocations, protections and segment ordering. There is no GNU-style linker script in this recipe.
- The saved `link.filelist` from CI 41340697398 has 1,105 object paths. `.LDFLAGS`, `all-alias.exp`, `all-kpi.exp` and `symbolsets.plist` are present. That build-tree archive deliberately excludes objects and libraries. CI 41543710742 includes a separate `.link` archive of compiled objects and link metadata. Its `.linkarguments` describes static kernel-cache relinking and adds the `__LASTDATA_CONST` rename. It is distinct from the final executable rule. The new diagnostics use the saved executable flags and explicitly identify the archived object substitution.
- The reference header is file-backed at offset zero in `__TEXT` at `0xfffffe0007004000`. The nonempty boot VM ranges follow `__TEXT`, `__DATA_CONST`, `__TEXT_EXEC`, `__KLD`, `__LASTDATA_CONST`, `__KLDDATA`, `__DATA`, `__BOOTDATA`, `__LINKINFO`, `__LINKEDIT`. Placeholder segments account for some differences between flag order and emitted headers. The file-only CTF extent has zero VM size. Segment and section lists and protections are in the [reference layout](../../../outputs/duchamp-full-xnu-source-build-20261117/reference-layout.json).
- `LC_UNIXTHREAD` supplies the ARM64 PC `0xfffffe0007480488`, the file-backed `__start` symbol in `__TEXT_EXEC,__text`. The file contains a symbol table and no undefined dynamic symbols. `tools/mkpayload.py::parse_macho` reads this PC and loads file-backed segments into the ADT-described window. The newer kernel must also define `_duchamp_dual_ramdisk_init` in executable text. Exact entry and registration addresses may move.

The [kernel validator](../tools/duchamp_xnu_link.py) checks the architecture, entry, link base, VM extents and protections, symbols and lack of a userspace loader. Normal dual-RAMDisk packaging invokes it. The archived image passes reference inspection and fails the candidate check on the missing registration symbol.
