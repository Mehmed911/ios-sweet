# Duchamp Darwin userspace status

This checkpoint uses the existing development XNU kernel from CI 41543710742, SHA-256 `e465723a540844817a5b9cb36c14984d660f9a8e41f6638240527b469189182b`. It exercises the 32 MiB HFS+ RAM-root path in ARM64 QEMU with an authored 0BSD C executable and an authored 0BSD static child. The C binary uses the locally held 20F66 restore dyld and libSystem. Apple runtime files are private test inputs. The QEMU profile attaches no block device. Physical UFS remains `BLOCKED_BY_FIRMWARE`. [Prior firmware assessment](DUCHAMP_FIRMWARE_UFS_OPTIONS.md)

## What the current XNU path supplies

| Area | Existing implementation and scope |
| --- | --- |
| PID 1 and launchd | The staged XNU `bsd/kern/bsd_init.c` creates the BSD init task. `bsd/kern/kern_exec.c:load_init_program()` resolves the executable. The 32 MiB **read-only** test uses the existing static `sweet-dynamic-init.S` as `/sbin/launchd` to set up the console, fork/exec the C child and independently reap it. A **separate writable RAM-root** test uses Apple's original `/sbin/launchd` as PID 1 and xpcproxy for real service launches. [Static harness](../tools/sweet-dynamic-init.S), [original launchd trial](../duchamp/LAUNCHD-QEMU.md), [service batch](../duchamp/PHONE-SERVICES-BATCH.md) |
| Mach-O, task and address space | `bsd/kern/kern_fork.c:fork1()` creates the child. `exec_mach_imgact()` in `kern_exec.c` calls `load_machfile()`, which constructs a user VM map. `parse_machfile()` maps segments and handles `LC_UNIXTHREAD`, `LC_MAIN` and `LC_LOAD_DYLINKER`. Exec installs the new map with `vm_map_exec()` and records dyld image metadata. A static executable can enter via its ARM thread state, while the dynamic executable executes dyld and reaches its C entry point. The new tests exercise 64-bit ARM64 startup, process identity, replacement of a forked child by exec, private file mapping and an invalid mapping. [Open-source XNU loader](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.121.2/bsd/kern/mach_loader.c), [VM syscalls](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.121.2/bsd/kern/kern_mman.c) |
| dyld and shared regions | XNU's `bsd/vm/vm_unix.c` contains the shared-region check and map/slide entry points, with implementation in `osfmk/vm/vm_shared_region.c`. The 32 MiB test sets `DYLD_SHARED_REGION=avoid` and uses 37 standalone restore-runtime files. It requires the guest dyld image list to contain libSystem. Prior work separately loaded the intact original shared cache from a larger read-only **virtual** disk and verified its UUID/range and cached Objective-C framework metadata. [Standalone runtime](../duchamp/DYNAMIC-USERLAND.md), [intact cache trial](../duchamp/SHARED-CACHE-QEMU.md) |
| Library and filesystem interfaces | The new C executable calls actual libSystem interfaces for directory iteration, `statfs`, open/read/close, `mmap`, `mprotect`, `munmap`, `fork`, `execve` and `waitpid`. The control executable and file come from the HFS volume that XNU mounts through `md0`. The driver and VFS code are reused. [HFS+ build patch](../xnu/patches/0026-sweet-builtin-hfs.patch), [read-only execution evidence](DUCHAMP_HFS_RAMROOT_EXECUTION.md) |
| Mach IPC and service lifecycle | The C executable checks a real Mach receive right, send right, message ID and payload through libSystem's Mach calls. This exercises in-task Mach IPC. The older launchd suite exercises separate processes, launchctl start/stop/restart and the notifyd/syslogd client paths with their original binaries in a separate fixture. [Mach message kernel path](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.121.2/osfmk/ipc/mach_msg.c), [launchctl lifecycle](../duchamp/LAUNCHCTL-QEMU.md), [XPC batch](../duchamp/XPC-BATCH-QEMU.md) |
| IOKit | The kernel reaches `PE_init_iokit()`, `InitIOKit()` and `ConfigureIOKit()`. `iokit/bsddev/IOKitBSDInit.cpp:IOFindBSDRoot()` resolves the ADT `RAMDisk` into a memory device. This boot exercises platform and BSD resource initialization and devfs. Application IOKit user clients and real MT6897 hardware are outside this test. [Open-source IOKit BSD initialization](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.121.2/iokit/bsddev/IOKitBSDInit.cpp), [prior QEMU compositor evidence](../duchamp/COMPOSITOR-QEMU.md) |

## Changes and remaining work

- The image builder can pre-create and verify the devfs mount point and can install the standalone static child and a file fixture with readback. The first QEMU run showed the direct dependency between the missing mount point and PID 1's console failure on a read-only root.
- The new probes rely on the existing loader, libc, BSD VM and IPC paths. No XNU loader or VM change was needed for this fixture. Ad-hoc image metadata and execution under the existing development policy supply no production signing evidence.
- To bring launchd service management and read-only root together, retain a separately writable volatile `/private/var` for launchd, service sockets and preferences, then replay the original PID 1 lifecycle on that layout. Extend the test to exercise cross-process Mach rights transfer.
- For graphical userspace, keep the 32 MiB profile as a fast regression. Use the separate QEMU fixture for the intact shared cache and larger frameworks. Verify real IOKit service matching and user-client replies, then reproduce the compositor frame and input path with the existing graphical fixtures. This checkpoint does not change the graphics, storage or input code.

The [execution report](DUCHAMP_HFS_RAMROOT_EXECUTION.md) records the fresh tests, process IDs, artifacts and commands.
