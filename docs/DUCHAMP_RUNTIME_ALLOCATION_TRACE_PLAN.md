## Minimum record to request from an existing supported producer

The existing normal-A log now proves that LK emits actual allocation events; the missing trace is specifically **B with actual XNU entry**. The [follow-up source audit](DUCHAMP_LK_BLACKBOX_HISTORY.md) establishes five cyclic positions for this writer and a pre-increment generation banner, but no supported historical export under the current restrictions. A particular B record's survival is unknown. An existing documented OEM export or matching vendor documentation is now required; do not invent a command, read a guessed physical/partition address or add another grant simulator.

Any recovered record must identify the slot and loaded images, allocation/free order, buffer completeness and actual entry. The supported capture path and retention must be established before proposing a new boot. Do not boot the uncertified enlarged candidate merely to gather evidence needed before its first write. Android A's `mb_avb` `[0x334a00000,0x33d600000)` must never be substituted for B. A capture on an independently approved existing baseline may validate the channel, but cannot transfer ownership to another image or boot.

A correlation ID or digest is useful for equality and ordering. It is not an ownership grant or proof of measurement origin. Evidence must have an identified producer, supported capture path and chain of custody; any claim of isolation needs a policy owner and verifiable coverage/lifetime. Do not require or invent a signature format that the installed firmware cannot emit.

The existing `blackbox` index `0x31a` agrees numerically with its decimal 794 message, but neither proves XNU executed or uniquely binds firmware to Android's later boot UUID. Counter wrap, reset, overwritten records and mismatched slots must be accounted for. The current A log has only a Linux-jump announcement; bootshim/XNU entry is a separate observation. Record firmware/DTB identities from an independently justified source; a matching Android build property alone is not the firmware digest.

## DMA and ownership evidence beyond the allocator map

An allocation snapshot establishes CPU-side bookkeeping. Separately account for each relevant master that could reach either low LK staging or the entire high XNU window.

1. Identify whether the master is powered/reset, actively submitting, retained by firmware, translated or bypassing an IOMMU. Establish how those conditions persist; a momentary idle sample is insufficient.
2. For translated traffic, identify actual stream IDs, protection domain, mapping tables/epoch and the ranges reachable by existing descriptors. The saved APU/display/MDP IOMMU nodes do not prove modem or UFS attachment.
3. For direct or remapped traffic, identify the effective EMI/SMPU/fabric apertures, access domains and any alias/remap window. A Linux DMA API mapping or absent DT `iommus` does not establish these policies at XNU entry.
4. Establish either verified exclusion over all candidate extents or a completed drain/fence plus continued exclusion. Include admitted interconnect transactions and stale translations, not only empty submission queues.
5. Identify firmware/other-processor writers, their buffer lifetimes, cache-maintenance responsibility and later policy owners. A cache operation or a CPU DSB/ISB is not a replacement for this ownership evidence.

The current saved evidence provides topology, source intent and now actual normal-A allocator activity, not this final B state. The A log's `clean pgd done`, protection-call return zero, modem-start message and reserved PGD name are useful source/capture landmarks. They do not expose effective master/stream IDs, bypass routes, table contents/epoch, completed drain or post-BL31 persistence. No UFS MMIO, reset or DMA probe is needed or authorized in this plan.

## If existing logs cannot retain the required boundary

The minimum instrumentation concept is observational, conditional on matching vendor source and an approved diagnostic path.

- Extend the existing `lib/mblock/mblock.c` reserve/free logging and the matching `boot_linux_fdt` implementation to report actual values and return statuses. Reuse an existing trace buffer only after its extent, ownership, capacity and retention are established. Do not choose a new arbitrary RAM address for logging.
- Capture input/mapping state before decompression and a final allocator event after the last release. Do not alter allocator decisions, reservation sizes, relocation, security policy or resource controls to make the trace look valid.
- Place a supported final-exit measurement after BL31's group-5 EMI/SMPU callbacks and subsequent final helper, before non-secure release. The saved handler is at file `0xb63c`, with named callbacks at `0x37150` and `0x3b5f8`. Matching source names for the complete final helper and supported diagnostic hooks still need vendor confirmation.
- Report only observable facts. Reading an allocated region or register does not itself delegate ownership. Policy/isolation assertions require the component able to enforce them, or independent validation of their documented effects.
- Reuse the existing bounded PC/x0/FDT collector to correlate input bytes. Keep raw firmware events distinct from bootshim-derived values and preserve unknown fields as unknown. No synthetic grant or new simulated authority is needed.

No applicable supported final-exit emitter is established for the reviewed retail firmware. The normal-LK log and `blackbox` retention lead do not fill this gap: messages are before the final policy boundary and contain no actual XNU-entry witness. Implementing the concept could require changing LK and BL31; it is **not executable under the current restrictions**. A copied patch from another MediaTek board, an undocumented SMC or a generic TF-A debug feature does not establish support on this device.

## Recovery implications and stop conditions

The instrumentation itself could prevent Android/recovery boot through an unaccepted firmware image, changed ABI, log-buffer overlap, stack exhaustion, timing disturbance or an incorrect entry path. Reading a reserved buffer can also fail if its access or lifetime is unverified. No firmware image, boot candidate or physical probe was changed to prepare this phase.

Before any separately authorized hardware proposal, verify current A recovery images against the installed Android build, exact original B rollback images, candidate hashes and Fastboot recovery reachability. Preserve the existing A installation, userdata and firmware. Use the established host rollback procedure to restore the verified B image set and select A only under that later approval. Do not construct a new recovery route or partition-write command from assumptions. [Recovery baseline](DUCHAMP_ANDROID_A_RECOVERY_VERIFICATION.md).

Stop dependent hardware authorization if a capture is from A or another boot, image identity is unresolved, raw records are missing/overwritten, a release status or later writer is unaccounted for, trace memory ownership is unknown, or master isolation lacks actual coverage and persistence. A may be used to validate a reader and format, as done here, but cannot clear B conditions. A successful QEMU decode or historical XNU photograph cannot clear them either.
