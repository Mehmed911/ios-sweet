# Duchamp firmware UFS options

**Physical UFS remains BLOCKED_BY_FIRMWARE.** The saved MT6897 firmware exposes some operations used by Xiaomi's Linux driver. The audited interfaces and logs supply no verified contract for transferring control of the UFS controller, excluding inherited DMA, or servicing the cache from XNU on Slot B. The supported immediate design is to keep the HFS+ root in RAM after stock LK loads the boot image. The evidence and hardware requirements for each resource are in the [resource control matrix](DUCHAMP_UFS_RESOURCE_CONTROL_MATRIX.md).

## Boot strategy

| Path | Feasibility and changes | Risk and evidence required |
| --- | --- | --- |
| **A. Firmware-assisted UFS handoff** | Blocked on stock firmware evidence. A supported firmware producer would have to preserve or explicitly transfer the controller, supply a final state receipt, and agree on queue, DMA and cache responsibilities with the existing XNU gate. LK's audited normal cleanup attempts PowerDown and clears HCE. The reviewed UFS SiP calls and retained logs supply no final-exit ownership record. | Reusing inherited descriptors can start stale work and place writes into XNU memory. Obtain a supported last-owner interface with same-boot final-state authentication, a complete drain and a continuing fence before reusing any resources. [LK shutdown](DUCHAMP_UFS_LK_SHUTDOWN_ANALYSIS.md), [final BL31 trace](DUCHAMP_FINAL_BL31_XNU_HANDOFF.md) |
| **B. XNU-owned cold initialization** | Preferred future UFS design. The existing test-only state machine covers ordered acquisition, reset, PHY readiness, DMA setup, IRQ policy, HCE and UIC. Production needs an exclusive, supported resource-control provider for the actual XNU boot, independent of inherited controller readiness. The current protected interfaces and kernel source do not establish that provider. | Reset or a shared clock/power vote can disrupt the old owner while DMA is still outstanding. Verify an enforceable fence and fabric drain before reset, checked access and transitions for each provider, a direct DMA filter or verified IOMMU stream/domain, and a complete cache contract. Keep the existing lease and release/failure rules. [Cold-init model](../duchamp/drivers/model/mt6897_ufs_init_model.c), [DMA safety](DUCHAMP_UFS_DMA_SAFETY.md) |
| **C. RAM root for initial XNU execution** | Verified for the 32 MiB diagnostic services root. Stock LK loads the boot bundle from storage. Bootshim materializes the embedded XNU and HFS+ image in RAM, the ADT describes `/chosen/memory-map/RAMDisk`, and XNU selects `rd=md0`. The historical Slot B services boot reached `launchd`, `notifyd` and `syslogd`. The fresh QEMU replay requires no configured UFS device. | The boot container, available RAM and loader layout limit the root size. The verified bundle supplies services and volatile state. It leaves the larger Setup root, durable storage and actual UFS isolation unverified. Preserve the stock firmware and verified Android A recovery path. [Phone services record](../duchamp/PHONE-SERVICES-BATCH.md), [Android A recovery verification](DUCHAMP_ANDROID_A_RECOVERY_VERIFICATION.md) |

## Offline change and verification

The [services packager](../tools/package-duchamp-services-candidate.py) checks the exact `rd=md0` RAM-root boot arguments, segment ranges, the embedded HFS+ extent against the guest proof's SHA-256, and the unique ADT `RAMDisk` mapping before it emits either image. Its receipt records the physical RAM-root range for each profile. This extends the existing preflight. The physical UFS gate, loader binary and signed-firmware components are outside the change.

| Run | Result |
| --- | --- |
| XNU services replay with no configured UFS device | **74/74** guest assertions in **71.357 s**. The run used the pinned, previously built XNU kernel and checked native `launchd`, `notifyd` and `syslogd` behavior. |
| RAM-root preflight regression | **10/10** archived-payload tests. Both layouts were accepted. Eight mutations were rejected, including a changed byte at the same image size, a changed root argument, wrong or missing ADT mapping and truncated metadata. |
| Local boot-image package | **13/13** checks, including host entry and materialization, real bootshim QEMU entry, and LZ4 and AVB container checks. The 32 MiB HFS+ root maps at `0x1c2568000` in both profiles. The 64 MiB locally rebuilt image matches the previously archived services boot image byte for byte, SHA-256 `545112503a5e9052db709572cc840758619f2b7e27c9aa58c0af2a3924a8f6a8`. |
| UFS regression and static evidence | Cold init **67/67** and handoff-format **98/98** in each of native ASan/UBSan and ARM64 QEMU. DMA route, cache, platform, pinned gate, saved LK/BL31 static audit and FDT provider inventory also passed. See the [matrix](DUCHAMP_UFS_RESOURCE_CONTROL_MATRIX.md#verification). |

Exact argv, exit codes, logs and image receipts are in [the verification directory](../../../outputs/duchamp-firmware-ufs-options-20261116). No connection to the phone was made. A and B remain hardware-blocked until an approved platform owner or independent hardware observer can provide the final-state and control evidence for the same Slot B boot.
