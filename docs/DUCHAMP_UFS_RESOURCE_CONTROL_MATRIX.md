# Duchamp MT6897 UFS resource control matrix

This audit uses the saved 485,760-byte Duchamp FDT with SHA-256 `9c49589f70044127be8941a9ea5537977f440ccd5ac15cfd24e120c8a1181d29`, the saved LK and BL31 images, pinned Xiaomi and Android kernel sources, and the archived Android observations. The stored ATF component previously read from both TEE slots matched byte for byte. The audit still lacks a measured record of executing BL31 at the Slot B XNU transition. [Recovery and firmware identity](DUCHAMP_ANDROID_A_RECOVERY_VERIFICATION.md), [pinned input and result receipts](../../../outputs/duchamp-firmware-ufs-options-20261116)

## Firmware interfaces

| Interface | Supported function or verified evidence | Needed for XNU |
| --- | --- | --- |
| PSCI | The saved FDT declares `/psci` as `arm,psci-1.0` with `method = "smc"`. The standard Linux client exposes CPU and system power functions. | PSCI supplies no peripheral UFS grant, UFS clock vote, reset, DMA fence or cache ownership. [Linux PSCI client](https://github.com/torvalds/linux/blob/v6.1/drivers/firmware/psci/psci.c) |
| SCMI mailbox | The saved FDT's `/firmware/scmi` links mailbox provider `0x35` to SRAM channels `0x36/0x37`. Its only declared child is MediaTek `protocol@80`. The archived Android endpoint bound to `scmi-tinysys`, reported vendor/subvendor `mtk`, protocol 1.0 and firmware revision `0x5353504d`. The DTB declares no standard SCMI clock, reset or power-domain provider on that node, and UFS points to different providers. | A supported protocol and resource description granting UFS control to the XNU boot. There is no evidence of a UFS resource in the declared vendor interface. A DT check cannot enumerate private firmware capabilities. [FDT provider trace](../../../outputs/duchamp-firmware-ufs-options-20261116/fdt-providers.log), [archived Linux report](../research/mt6897-live-evidence/14480520-210535/runtime-report-v3.json), [standard binding](https://github.com/torvalds/linux/blob/v6.1/Documentation/devicetree/bindings/firmware/arm,scmi.yaml) |
| MediaTek UFS SiP | Xiaomi's `MTK_SIP_UFS_CONTROL` client declares operations for reference-clock notification, MTCMOS, device reset, PHY and power controls and MCQ configuration. The saved BL31 static audit verifies the service descriptor and the reference-clock, MTCMOS and MCQ dispatch paths. The MCQ query supplies configuration to the Linux driver. The saved BL31 has a common zero-return path that can hide an operation-specific failure. | Need the supported caller contract for Slot B XNU, checked results, independent state readback, constraints and resource lifetimes. A service ID and a successful return cannot establish ownership, a live queue state, or an actual transition. [Xiaomi SiP client](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/ufs/ufs-mediatek-sip.h#L12-L96), [saved BL31 SiP audit](../research/mt6897-firmware-live/20261101-v1/ufs-sip-audit-v2.json) |
| Measured handoff and debug logs | Existing ATF, LK and pstore logs are useful for firmware and sequence identification. No reviewed interface exports an authenticated final BL31 exit paired with the actual XNU entry and UFS grant. The current project can record bootshim entry and DTB identity and check a separately sourced receipt. | A supported firmware producer or approved independent observer must attribute each assertion to its actual owner and bind it to a fresh Slot B and XNU boot. Bootshim state and hashes identify its inputs. They cannot observe private firmware resource ownership. [Final handoff audit](DUCHAMP_FINAL_BL31_XNU_HANDOFF.md), [handoff format](DUCHAMP_UFS_HANDOFF_FORMAT.md) |

## Resources required for exclusive cold initialization

| Resource | Board and code evidence | Required before physical access |
| --- | --- | --- |
| HCI and firewall | `/soc/ufshci@112b0000` declares the aperture `0x112b0000/0x3000`. The saved BL31 kernel-boot path performs EMI/SMPU work after LK cleanup. DT topology and Android mappings show where its Linux driver operates. | Same-boot effective non-secure MMIO policy and explicit exclusive ownership for the needed ranges and their lifetime. No permission is inferred from an Android mapping or an address in a table. [Saved LK and BL31 report](../../../outputs/duchamp-firmware-ufs-options-20261116/lk-bl31-audit.json), [final handoff audit](DUCHAMP_FINAL_BL31_XNU_HANDOFF.md) |
| Clock muxes, gates and reference clock | Twelve UFS clocks resolve to MediaTek TOPCKGEN `0x69`, UFS AO `0x65` and UFS PDN `0x64`, including UniPro, HCI and AES gates. The vendor driver handles separate reference-clock notification and a request/ACK handshake. | Approved ownership of the muxes, parent rates and hardware votes, checked gate and reference-clock state, and the required interval of stable power. Preserve clocks shared with another owner. [TOPCKGEN muxes](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/clk/mediatek/clk-mt6897.c#L2457-L2477), [AO and PDN gates](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/clk/mediatek/clk-mt6897-peri.c#L274-L327), [reference clock](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/ufs/ufs-mediatek.c#L416-L470) |
| Rails, domain and PHY | The UFS node declares `vcc`, `vccq`, `dvfsrc-vcore`, and the RTFF/MTCMOS policy, with no HCI `power-domains` property. The PHY is v1. The common legacy analog power path returns early at that version. Linux uses regulator, runtime PM, clock and PHY framework state in addition to the SiP client. | A supported owner of each rail, domain and PHY, documented bring-up and readiness checks for PHY v1, and readback of retention and effective MTCMOS state. Static firmware dispatch alone does not establish readiness. [MediaTek init](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/ufs/ufs-mediatek.c#L1524-L1627), [PHY version path](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/phy/mediatek/phy-mtk-ufs.c#L152-L179) |
| Host reset and device reset | The node declares `unipro_rst`, `crypto_rst` and `hci_rst` via the PDN reset controller. By separate static cross-reference, the saved BL31 conditional store to bit 0 of `0x112b8090` controls the active-low UFS **device** reset level. The audited paths leave physical assertion and release unobserved. | Verify authority and actual state separately for host and device resets. Establish fencing and fabric drain before any reset, then confirm PHY and reference stability through the transition. [Host reset sequence](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/ufs/ufs-mediatek.c#L276-L350), [device reset routine](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/ufs/ufs-mediatek.c#L1935-L1958), [BL31 cross-reference](DUCHAMP_UFS_OWNERSHIP.md#identifying-the-always-on-syscon-bit) |
| Queues, interrupts and link | Saved LK code attempts PowerDown, then clears HCE without reporting completion or sampling all final queues. Android configures MCQ using capability discovery and the vendor IRQ paths. The common driver starts the link using UIC only after platform setup. | Verify producer shutdown, queue mode and all transfer, task and configured MCQ queues, including pending IRQs. Require an independent fabric-drain acknowledgment and an enforceable no-resume fence. Only then can an authorized exclusive initializer configure bounded HCE, UIC and IRQ handling. [LK shutdown](DUCHAMP_UFS_LK_SHUTDOWN_ANALYSIS.md), [vendor MCQ IRQs](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/ufs/ufs-mediatek.c#L2949-L3016), [common link sequence](https://github.com/aosp-mirror/kernel_common/blob/cf2c2dc91b9e9f016dc25cf095b1fe34cb5dfcb6/drivers/ufs/core/ufshcd.c#L4757-L5014) |
| DMA route and isolation | `/soc/dma-ranges` declares a 36-bit identity aperture, and the UFS node has no `iommus` property. Archived Linux saw generic DMA-direct, no standard Linux IOMMU attachment, 64-bit DMA masks and a 36-bit bus ceiling. An observed SWIOTLB pool leaves the actual bounce decision open. | For direct DMA, establish effective translation, bounce policy and an enforceable per-master filter for the XNU range. For translated DMA, identify the actual UFS stream and route, own the domain and mapping epoch, retire stale mappings and verify completed invalidations. Both need drain and no-resume evidence. [DMA route evidence](../duchamp/MT6897-DMA-IOMMU-FIRMWARE-EVIDENCE.md), [Linux DT DMA setup](https://github.com/aosp-mirror/kernel_common/blob/cf2c2dc91b9e9f016dc25cf095b1fe34cb5dfcb6/drivers/of/device.c#L114-L218), [MediaTek IOMMU source](https://github.com/MiCode/MTK_kernel_device_modules/blob/3c4ccd07d5624879555ec710c11bb8818e5cb5c6/drivers/iommu/mtk_iommu.c) |
| Cache and descriptor lifetime | The captured UFS node does not declare `dma-coherent`. Linux coordinates its own buffers with the DMA API. A read-only command still causes device writes into RAM. CPU ordering, CPU cache maintenance, any outer cache, and peripheral/fabric drain are separate. | Identify the actual coherency domain and owner of system-cache maintenance, verify synchronization at the device-visible point for the target range, and quarantine inherited descriptors until drain and fence are proved. [DMA cache rules](DUCHAMP_UFS_DMA_SAFETY.md), [Linux DMA API](https://docs.kernel.org/core-api/dma-api-howto.html) |

The existing gate remains the authority for future activation. Adding a clock or SiP client without the other proofs would leave resource authority unresolved. The [offline initialization model](../duchamp/drivers/model/mt6897_ufs_init_model.c) stays test-only. The RAM-root route is independent of XNU's UFS providers. [Boot strategy](DUCHAMP_FIRMWARE_UFS_OPTIONS.md#boot-strategy)
